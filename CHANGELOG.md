# Changelog

**For:** anyone who cloned this template and wants its updates.

One line per publish, newest first: the date, what you have to do after
`git pull --no-rebase template main` that the pull cannot do for you, and
who wrote any pull request the publish carries. How to set up that remote,
and why your copy has to be a private repository rather than a GitHub fork,
is in the README, *Keeping your work, getting updates*.

Each publish is a commit whose parent is the previous publish, so a pull is an
ordinary merge. A conflict inside `deliverable/` or `generators/` means that
exercise's stub changed under your work: keep your code, and read the line
below for what changed and why. The chain starts at the 2026-10-09 publish,
which replaced every earlier one: a copy of any publish before it shares no
history with it and cannot pull, so start again from a fresh copy (the README,
Quickstart step 0) and copy across the files you wrote in `deliverable/` and
`generators/`.

- 2026-10-12: an ordinary pull this time: outside the dev container there is nothing to run again. In the dev container, the setup script of a container made from the 2026-10-09 publish stopped at its first step, so `42` is not on its PATH (and under Antigravity its extensions are missing): after the pull, run `sh .devcontainer/postcreate.sh` once in the container's top folder and open a new terminal (until `42` is found there, `sh tools/42.sh` is the same command; rebuilding the container runs the script too, but empties Bazel's caches). The script now also gives the container's Bazel a disk cache (docs/environment.md, *Dev container*). New: `42 config` shows and changes your settings (login, email, level, each project's Vogsphere URL, how many CPUs Bazel uses and how long its server waits idle), in the files they already lived in (`42 config list --all`; docs/testing.md, *The `42` command*). `42 submit URL`, the first time, saves the project's URL in `.submit-remotes` and pushes there, and the next `42 submit` needs none (a `.submit-remotes` you wrote keeps working, and its keys may now be the short names, `c-00`). `42 submit --written-only` pushes the exercises you have written and lets the ones still a stub through the gate. It refuses a project with nothing written, and in C 00, Shell 00 and Shell 01, whose subjects say where their mandatory part ends, a project with an exercise of that part still a stub (docs/submitting.md). `42 submit ex03` and `42 generate ex03` now refuse the exercise's name, where they acted on its whole project. What changed, so a test that was green on your work can be red now (its log says what it observed): at basic, C 04 ex00's and ex01's output tests have a case of 5000 characters, and BSQ has a new `ex00_full_in_body_output`, a map with the full character in a row, which accepts either verdict a reading of the subject can give (its README); at strict, many `diff` corpora (C 01 to C 04, C 06, C 07, C 11, and Piscine Reloaded's copies) now hold strings past 4096 bytes, more than 4096 ints or more than 1024 arguments, Reloaded's ex18 and ex19 replay C 06's argument corpora (`ex18_argv_diff`, `ex19_argv_diff`, and `ex19_high_bytes_argv_diff` at robust), and BSQ's `ex00_readings` adds that map; and Rush 00's `ex00_rush0N`, which you ask for by name, now runs all of its variant's tests, four more than before. No test was renamed or removed, and none changed level.
- 2026-10-09: this publish rewrote the template's history, so a copy of any earlier publish cannot pull it: some of their text (the exam guide's walkthroughs, some hints, a few comments) gave away more about named exercises than a template should, and every commit that held it is gone. So start again. In your old copy, run `bazel shutdown` (its server otherwise keeps its memory for up to three idle hours), and move the copy aside if it is `~/42` (`mv ~/42 ~/42-old`). Then make a fresh copy as the README's Quickstart step 0 says, and run `sh tools/setup.sh` in it: it records where Bazel keeps its state, a per-user place by default now (docs/environment.md), and puts `42` on your PATH, a front-end that types the Bazel commands for you (`42 test` in a module's or an exercise's folder, `42 watch`, `42 clues`, `42 submit`; docs/testing.md, *The `42` command*; `sh tools/42.sh` is the same command), which needs python3 3.10 or later, as Ubuntu 22.04, the campus system, ships. Copy across only the files you wrote in `deliverable/` and `generators/`: a stub you never touched is better taken from the new copy, since some changed (Rush 00's `rush0N.c`; the opening comment of the BSQ and C 11 ex05 Makefiles, and of Shell 00's ex03, ex05, ex06 and ex08 generators and of Reloaded's ex02; Shell 00 ex05 and ex06 need no execute bit, as each generator's comment now says). As you copy: BSQ turns in at `c-piscine/c-piscine-bsq/deliverable/` itself, not `deliverable/ex00/`, because its subject names no turn-in directory, so your files go one folder up; C 09 ex01 turns in the Makefile alone (the grader supplies `srcs/` and `includes/`); Rush 00 turns in no header, so leave `rush.h` behind and take its `#include` out of your `rush0N.c` (a function that is then undeclared is declared in the file that calls it), write your team's variant in `c-piscine/c-piscine-rush-00/team.bzl`, and delete the `rush0N.c` stubs you do not owe; C 12 ex08's `ft_list.h` is the grader's, and your copy is optional; Rush 02's `numbers.dict` has one place, `c-piscine/c-piscine-rush-02/deliverable/ex00/numbers.dict`, where it is turned in and where the harness reads it; 42's own files for Shell 00 and Rush 02 each have a `*.DOWNLOAD-ME.txt` placeholder in the project folder naming the exact path it goes to; and your Vogsphere URLs go in `.submit-remotes` (docs/submitting.md), not in `tools/submit.sh`. New: where to take a question or a problem, in CONTRIBUTING.md, SUPPORT.md and SECURITY.md, with a form for each kind of issue; a check that is wrong about what an exercise must do is reported privately, never in a public issue, since showing it takes exercise code. What changed, so a test that was green on your work can be red now (its log says what it observed): the `files` test is stricter, at basic: it reads every subfolder of the turn-in, each module's files outside every exercise folder (`//<module>:deliverable_files`), and, where your Makefile builds the project, a `.c` it never compiles, and whatever it names blocks that module's push, so delete it or move it out of `deliverable/`; other checks read more inputs or moved to basic, and C 07 ex04's `ex04_base_to_space_output` from robust to strict; Shell 01 ex04 and Reloaded ex04 (MAC.sh) are no longer manual, so `bazel test //...`, their `:basic` and `//tools:submit`'s gate check them (a machine with no network interface to show says SKIP), and a MAC.sh that is not finished blocks that module's push like any other exercise; some tests were renamed or merged, Rush 00's `ex00_rush0N_robust` among them, now `ex00_rush0N_survive`, so a command you saved may need the new name (`bazel query //<module>:all` lists them). `//tools:submit`'s gate now runs in the same Bazel output base as your own commands, restarts Bazel's server before the first module and trusts no cached result, so each gate builds and runs the module's tests again: slower than a cached run, but it cannot pass on a result left by a file saved while a test ran. The output base it had of its own is unused: free its gigabytes with `bazel --output_base=PATH clean --expunge`, run in your old copy, PATH being the `bazel-gate` folder beside the `bazel` one that holds `bazel info output_base` where you ran `sh tools/setup.sh`, and `~/.cache/_bazel_submit_gate` where you did not; `SUBMIT_GATE_OUTPUT_BASE` is read by nothing now. Every prime, the one at login and `bazel run //tools:prime` alike, now writes down what the machine did while it ran (memory, swap, the disk queue, each Bazel server's memory) in a small file under `~/.local/state/42-piscine/prime-traces/`, in a folder named after the machine, the five newest of each kept; a login prime that stopped with the machine is not started again by itself: it says so when you open a terminal, `sh tools/env-audit.sh` puts the file in its report, and `bazel run //tools:prime` lifts it.
